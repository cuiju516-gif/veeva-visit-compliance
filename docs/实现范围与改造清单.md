> ③ 删除窗口按 §3.2 迁移 5 的两个条件同时成立。

## 1. 范围冻结

| 层 | 内容 | 理由 |
|---|---|---|
| **必做** | 五步流程 · schema · 4 个接口 · R1/R2 双规则 · 看板 · 单测 · `docker-compose` | 题面逐条列的，直接占分 |
| **值得做** | 规则版本 + 判定快照（`角色模型` R-ROLE-2）· 取消/作废（带原因、留痕）· 看板 5 个数字 · actor 与数据范围 | 都是 schema 层的小改动，但直接对应 `需求说明` §12 的验收点 |
| **只写不实现** | RBAC 权限矩阵 · 主数据 CRUD 与变更审计 · 异常复核流 · 超时调度器 | 题面明说「不要求完整认证与权限」；写进设计说明即可得分，真做会吃掉全部时间 |

**判断依据**：题面的评分重心是「合规算法 + schema 是否支撑五步 + 一键部署 + AI 报告」。角色/权限/主数据
是加分项，但它们的成本是必做项的 2–3 倍。

## 2. 十条验收各自意味着什么（与实现无关的读法）

这一节只回答「这条验收在代码里要求什么」，不判断谁的实现做到了几条。

| # | 验收点 | 落到代码上是什么 |
|---|---|---|
| 1 | 代表只能看到本人拜访 | 每个查询都要带 actor，并在**服务端**过滤；越权返回 404 而非 403（不泄露存在性） |
| 2 | 签到/签退时间由服务端生成 | 时间戳不接受客户端字段；未知字段应报 400 而不是被忽略 |
| 3 | 299s 异常 / 300s 合规；499.9m 合规 / 500.1m 异常 | 两个比较必须是严格不等：`duration < 300`、`distance > 500`（含浮点容差策略） |
| 4 | 双重异常返回 **3 项** | 见 §4 的约束陷阱：R1 一条 + 每个偏离点各一条，共 3 条 |
| 5 | 三种非法流转 → 409 | 状态守卫要在写操作里，而不是先读后写 |
| 6 | 取消需原因 / 删除免原因限窗口 / 作废仅已签到 | 三个动作各自独立，且都要落 `who/when/why`；作废不物理删除 |
| 7 | 作废时补判 R2 | 补判要在写 flags **之前**，结果写进作废记录，不能因作废而消失 |
| 8 | 改阈值生成新版本，历史判定不变 | 判定必须存快照（阈值 + 规则版本 + 判定时间），不能只存布尔或原始文案 |
| 9 | 主数据逻辑删除，历史靠快照可读 | 拜访落库时快照展示所需字段；主数据删除只打标记 |
| 10 | 看板五个数字与口径一致 | 完成 / 有效 / 异常率 / 取消 / 作废，删除不入分母；依赖 6 的状态与原因字段 |

| # | 改动 | 影响面 | 量级 |

| 1 | `status` 枚举 4 → 7（加 `CANCELLED` / `VOIDED` / `DELETED`） | 状态机、约束 `chk_visit_state_evidence`、前端渲染 | M |

## 4. 一处会被 schema 卡住的需求：逐点判定 vs 唯一约束

`需求说明.md` §4 规定地点规则**逐点判定，各生成一条**：签到点偏离、签退点偏离，各自一条
`LOCATION_DEVIATION`。一个两点都偏离的拜访，flag 表里必然出现**两行同 code** 的记录。

所以 `visit_flag` **不能**加 `UNIQUE (visit_id, code)`。加了之后，第二行插入会失败，把一次真实的
合规异常变成服务端错误（要么整体回滚，要么丢掉一条证据），而且这条路径恰好只在「异常最严重」的
时候触发，测试很容易漏掉。

两种建模都可接受：

- **A（推荐，贴合 §4 原文）**：不加唯一约束，`code` 只表示规则，行数表示命中次数；
- **B**：拆成 `LOCATION_DEVIATION_IN` / `_OUT` 两个码——但这样「一个码 = 一条规则」不再成立，
  按规则聚合时要再合并。

选定后要写进 schema 注释，否则下一个人会"顺手"把唯一约束加回来。

## 5. 建议施工顺序（每步一个可提交的切片）

1. **先定 flag 的唯一性口径**（§4），并写一条「两点都偏离 → 3 条」的用例。
2. **状态机 4 → 7**：domain 的迁移表、`chk_visit_state_evidence`、接口错误码、前端状态渲染。
3. **取消 / 作废 / 删除** 三个动作 + 原因 + 留痕；作废时补跑 R1/R2。
4. **判定快照 + 规则版本**：`evaluation` 落库，看板可按版本筛。
5. **看板 5 个数字**：完成 / 有效 / 异常率 / 取消 / 作废，删除不入账。
6. **actor 与数据范围**：`X-Actor` 头 + 服务端过滤；越权返回 404。
7. 主数据快照 + 逻辑删除（可与 4 合并）。

前 5 步覆盖验收点 1–10 中的 1、4、6、7、8、10；第 6 步补 1；第 7 步补 9。

## 6. 三个容易反复的点

1. **`CHECKED_OUT` 计入完成**，`REPORTED` 只代表「记录完整」——看板的"完成"不能只数 `REPORTED`。
2. **作废补判**必须发生在「写 flags 之前」，且 flags 属于作废记录，不能让作废把异常抹掉。
3. **删除不入任何分母**，但行要留在库里（`DELETED` 终态），否则「计划执行率」的分母可被任意收缩。
