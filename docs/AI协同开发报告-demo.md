# AI 协同开发报告 · 交互原型（`demo/`）

> 范围：本文只覆盖 `demo/` 这套交互原型（纯静态、可点击、含 15 条单测）。
> 仓库主交付（Go + Postgres + `web/`）的协同报告是 `AI-COLLABORATION.md`，两者独立，互不替代。

---

## 1. 工作方式

一条规则贯穿全程：**每一轮只改一个可验证的小目标，改完立刻截图 + 跑测试**。

原因很实际——原型的价值在于"点得出来"，而"点得出来"只有真浏览器能证明；
`node --check` 只能证明语法，证明不了行为。

| 阶段 | 产物 | 用来回答的问题 |
|---|---|---|
| 1 | 需求提取 | 题面到底要求了什么、哪些是留白 |
| 2 | 可点击原型（happy path） | 五个步骤能不能走通 |
| 3 | 角色切换 + 权限边界 | 三种角色看到的东西是否真的不同 |
| 4 | 状态机（7 状态 / 8 迁移） | 哪些动作在哪些状态下合法 |
| 5 | 规则与统计口径 | 五个数字怎么算、为什么这么算 |
| 6 | 冲突消解（作废 / 删除 / 快照） | "不作数"有几种，彼此怎么区分 |

## 2. 关键 Prompt 记录

以下是驱动本原型的关键指令（原文），以及每一轮做出的设计判断。

| # | 指令（摘要） | 触发的最关键判断 |
|---|---|---|
| P1 | 「给出简单的前端 demo，帮助我从交互理解 happy path 和主要分支」 | 不做 CRUD 展示，只做**判定可见**：异常必须在点击的瞬间出现。于是引入"虚拟时钟"——否则演示一次"停留不足 5 分钟"要等真实时间 |
| P2 | 「系统的直接使用者至少包括 3 个：MR / 主管 / 管理员」 | 角色决定**数据范围**而不只是按钮：同一句"按产品统计月度拜访次数"，三个人是三种 WHERE。schema 必须有 `mr_id` / `team_id`。**（后来被推翻，见 §3.8）** |
| P3 | 「MR 默认页应是 plans list，可按开始时间/状态/异常类型排序」 | 列表先行，详情次之；排序键要能对"异常类型"分组，不能按字符串排 |
| P4 | 「修改/删除未结束的 plan 并标注原因」 | 区分三种"不作数"：删除=录入错误、取消=主动放弃、作废=到了不算 |
| P5 | 「作废和删除该如何区分呢」 | 用**时间窗**而不是严重程度来分：事前可删/可取消，事后只能作废 |
| P6 | 「是否需要加一个状态机帮忙决定允许删除还是取消，还是只靠系统时间检查？」 | **不加状态**。时间是谓词（`canDelete(v, now)`），状态只记录事实；加了状态会随时间自己变，还要靠调度器维持，调度器一停就和现实脱节 |
| P7 | 「删除也是终态吧」+ 完整迁移说明 | 采纳为 `DELETED` 终态；同时把"计划超时"从作废改为**取消**（作废的前提是"人到了"） |
| P8 | 「操作按钮能否用三个点替换，只显示可用的操作」 | `⋯` 菜单按状态渲染；不可用的动作**不出现**，但底部留一行说明，避免"功能坏了"的错觉 |
| P9 | 「使用快照方案，但数据库仍不删除，而是标记删除、不用于展示」 | 拜访快照姓名/科室/药品/医院坐标 → 主数据可以逻辑删除而历史不受影响；代价（改名不回溯）写进文档 |
| P10 | 「能否要求填报了记录才能签退？」 | **不接受硬前置**：签退时间戳是 R1 的输入，等填完记录再签退会污染时长。改为"签退锁定时间 + 立刻弹记录表单"（一次操作、两个时间点） |
| P11 | 「哪些内容会是审计需要的？」 | 审计只问三件事：发生过吗 / 为什么这么判 / 事后动过吗。据此反推必须留存的字段 |

### 被采纳 / 被否决的 AI 建议

| 建议 | 结果 |
|---|---|
| 用谓词函数而不是状态表达"能不能删" | ✅ 采纳（P6） |
| 保留 `CHECKED_OUT` 作为独立状态，不要合并进 `REPORTED` | ✅ 采纳（否则"签退没填记录"无法表达） |
| 姓名类字段走 join 而不是快照 | ❌ 否决（P9 要求全快照，代价已写入文档） |
| 作废需要主管审批 | ❌ 否决（改为代表自助 + 补判 + 事后审计） |
| 给"1 小时内开始"的计划加二次确认 | ✅ 采纳 |

## 3. AI 纠偏亮点案例：用 demo 把状态机"点"出来

> 这是本原型最有价值的一次协同：**AI 给出的第一版状态机只覆盖了 happy path，是「点着点着」才补全的**。
> 下面按真实顺序记录讨论与发现。

### 3.1 起点：AI 的"字面实现"

最初的状态机只有四个正向状态，全部来自题面的五个步骤：

```
PLANNED ──签到──► CHECKED_IN ──签退──► CHECKED_OUT ──补记录──► REPORTED
```

它是对的，也是**不完整的**：这条链路只能表达"去了、且走完了"，表达不了任何"没去成 / 去了不算"的现实。
而现实里，医生停诊、临时改期、走错院区每天都发生。

AI 当时的判断是"题面没写，就不做"——这是字面实现，不是需求理解。

### 3.2 第一次发现：删除不该是一个数据标记

候选人提出"默认页应该是计划列表，能改、能删、能取消"。AI 的第一版实现是：

- 取消：`PLANNED → CANCELLED`（进状态机）
- 删除：**一个 `deleted` 字段**，从列表里过滤掉（不进状态机）

在 demo 上点了两次之后问题暴露出来：**删掉的计划去哪了？**

- 它不在"完成"里，不在"取消"里，也不在"作废"里；
- 看板的"计划执行率"因此算不出来——分母可以被删除任意收缩；
- 审计问"这条计划存在过吗"，答不上来。

**判断点**：删除不是"看不见"，而是一个**业务终态**。候选人的表述很直接——"删除也是个终态状态吧"。

于是 `DELETED` 进入状态机，并补了两条规则：
1. 删除**免原因**（它是纠错，不是业务事件）；
2. 但只有"创建后 1 小时内 + 距开始 > 1 小时"才允许，超出窗口只能取消（取消需原因、进取消统计）。

这一步把"删除"从数据层操作提升成了业务语义，也让 `取消 vs 删除` 第一次有了清晰边界：
**删除 = 本来不该存在；取消 = 主动放弃。**

### 3.3 第二次发现：作废不该要审批（AI 的过度设计）

有了删除和取消，AI 接着加了"作废"，但设计成**两级审批**：

```
CHECKED_IN ──作废申请──► PENDING ──主管确认──► VOIDED
```

理由写得很"稳"：怕代表把异常拜访作废掉，所以要主管把关。
（后来主管整层被裁掉，这条设计连"谁来批"都无从谈起——见 §3.8。）

候选人直接否掉："不需要主管审核，直接作废。"

讨论后承认这是 **AI 的过度设计**：医生停诊是**高频事件**，如果每次作废都要等主管，代表会怎么选？
他会选择**不作废、直接走人**——让系统 24 小时后自动处理。结果是数据更脏，而不是更干净。

**判断点**：审批解决的是"信任问题"，但它把成本压在了每一次**正常**作废上。真正该做的是
**让作废无法掩盖事实**，而不是让作废变慢。于是改成：

- 代表自助作废，但**必须填原因**；
- 作废时**补跑 R1/R2**（用已有的签到时间与坐标），把 flags 存进作废记录；
- 看板把"作废"单列一栏，异常在作废记录里仍然可见。

这样作废只能让这条拜访"不计入完成"，不能让异常"没发生过"。
（当时写的是"主管能看到"；主管角色在 §3.8 被裁掉后，这一栏改由管理员看。）

### 3.4 第三次发现：超时到底算取消还是作废

AI 第一版的超时扫描**只处理了"签到未签退"**——计划过期未签到根本没有任何出口，
会永远停在 `PLANNED`。这又是一次字面实现：题面里的"拜访"从签到开始，
所以 AI 只想到了签到之后的悬挂。

候选人指出："planned 超时 24 小时应该也是作废"。

但在实现时发现口径对不上：**作废的前提是"人到了"**（有签到证据），
而"计划过期没去"根本没有到过现场——把它记成作废，会让作废率混进一批
从没进过医院的人，这个指标立刻失去含义。

**判断点**：两条系统边，终点不同——

| 场景 | 终点 | 理由 |
|---|---|---|
| 计划时间 + 24h 未签到 | `CANCELLED`（NO_CHECKIN） | 没去成，属于取消 |
| 签到 + 24h 未签退 | `VOIDED`（TIMEOUT） | 去了但没走完，属于作废 |

这是本次协同里**唯一一次 AI 反过来修正候选人的口径**：作废只从 `CHECKED_IN` 出，
计划阶段的两个出口是「取消」和「删除」。

### 3.5 第四次发现：作废窗口必须关在签退之前

AI 的第二版允许 `CHECKED_IN` 和 `CHECKED_OUT` 都能作废。

在 demo 上走一遍就看出问题：**签退之后，界面已经显示"异常 · 命中 2 项"，此时再点作废，
等于判定可以被撤销。**

**判断点**：作废与判定是"抢跑"关系——判定发生在签退，作废发生在判定之前，
代表就能在"估计要判异常"时提前作废。把作废收紧为**只允许 `CHECKED_IN`**，
这条路就由状态机本身堵死了（不是靠制度，是靠没有那条边）。

### 3.6 收敛后的状态机

**7 个状态 · 8 条迁移**，其中两条是系统边：

```
PLANNED ──签到──► CHECKED_IN ──签退──► CHECKED_OUT ──补记录──► REPORTED
   │                  │
   ├─取消(需原因)─► CANCELLED          ├─作废(需原因)─► VOIDED
   ├─删除(免原因)─► DELETED            └─超时(系统)───► VOIDED
   └─超时(系统)──► CANCELLED
```

三个终态各归一个计数器：**完成**（CHECKED_OUT + REPORTED）/ **取消** / **作废**，删除不入账。

### 3.7 复盘：AI 在这一轮里的四类错误

| 错误类型 | 具体表现 | 人的纠正方式 |
|---|---|---|
| **字面实现** | 题面没写退出路径，就不设计退出路径 | 用真实场景（停诊、走错院区）去压测状态机 |
| **过度设计** | 给作废加两级审批，理由"更安全" | 问"这个成本落在谁身上、多久一次"——高频场景下审批会逼出更差的行为 |
| **语义混淆** | 把"删除"当数据标记而不是终态 | 追问"这条记录还该不该被统计到"——能算进分母的才叫状态 |
| **漏掉出口** | 超时只处理了"签到未签退"，"计划过期"没有出路 | 拿状态逐个问"如果一直停在这里会怎样" |

共同点：**AI 的每一版单看都自洽，只有在"点一遍 + 问一句'那这条算哪一类'"时才暴露**。
所以这个 demo 的真正作用不是展示界面，而是**把状态机变成可以被质疑的对象**。

> 这一轮的产物：`demo/assets/state-machine-v2.svg`（图）与 `需求说明.md` 第 3 节（表）。

### 3.8 补记：需求自己的收敛——三类使用者砍成两类

> 这一条不是 AI 的错误，是**需求在被实现之前自己收窄了**。记在这里，是因为"能砍掉自己加过的东西"
> 和"能发现 AI 的错误"一样，属于同一件事的两面。

**发生了什么**：到契约阶段，需求方把「区域主管 DM」整层砍掉，理由三条——
① 团队维度的成本不在查询而在**组织模型**（团队表、成员变更、跨区、代理），而它只服务一个角色的一天一次的操作；
② 题面要求的看板是"**按产品维度**统计"，产品维度与团队维度正交，管理员用全量数据就能回答；
③ 异常复核从未进入实现范围，而它唯一的用户就是主管。

**代价被明确接住**：主管的"看数"能力没有消失，转给了管理员（全量、只读）；"复核"没有替代物，
机器判定仍然不可变，也就没有了"两套结论并存"的问题。

**AI 这一轮做错的地方**：第一版 schema 直接加了 `mr.team_id`，还把它写进了裁决记录（6-4）。
角色一砍，这条列立刻变成死字段——**加一个字段只要一行 DDL，删掉它要改 ERD、契约、ADR 三处**。
这条教训进了 `契约 §6`：

> 6-4 撤销。若日后要恢复团队视角，是重新引入角色 + 组织模型，不是加一列。

**同步落地的资产**：`需求说明.md` §1/§5/§8、`角色模型.md`（重写为两类，主管进"已裁掉"）、
`契约.md`（去 team_id、actor 收窄、看板按 actor 收窄）、`adr/0002`（补记 6-4 撤销）、
以及 `demo/`（轨道 4 档 → 3 档，团队看板与复核队列删除，管理员新增「月度看板」Tab）。

## 4. 验证手段

| 手段 | 覆盖什么 | 命令 |

| 单元测试 | 边界值（299/300 秒、499.9/500.1 米）、状态机迁移、统计桶互斥 | `node --test demo/logic.test.mjs`（15 条） |

## 6. 局限

- `demo/` 的数据在内存里，刷新即重置；它证明的是**交互与规则**，不是持久化。
- 虚拟时钟只影响签到/签退时间戳，真实系统必须由服务端盖章。
- 超时扫描在每次渲染/每秒 tick 时跑，真实系统应交给幂等的定时任务。
- 审计所需的"主数据编辑 before/after""访问与导出日志""系统扫描批次记录"尚未实现，已在
  `需求说明.md` 第 10 节标为缺口。
