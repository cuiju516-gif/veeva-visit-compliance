## 1. 工作方式

一条规则贯穿全程：**每一轮只改一个可验证的小目标，改完立刻用最接近真相的方式验证。**

"最接近真相"是逐级升格的，因为每一级都能证明上一级证明不了的事：

| 级别 | 能证明 | 证明不了 |
|---|---|---|
| `go build` / `tsc` | 语法与类型 | 任何行为 |
| 单元测试 | 规则、边界、状态机 | 数据库约束、真实渲染 |
| 真库集成测试 | 约束、事务、幂等 | 界面上到底能不能点 |
| 无头浏览器 + curl | 真实渲染、真实 HTTP | 换台机器还能不能跑 |
| 容器里跑 compose | 部署路径 | —— |

这条链子后半段是这次最费时间、也最值钱的部分：**前三级全绿、第四级才发现的问题有四个**（见 §3.2）。

### 阶段与产物

| 阶段 | 产物 | 用来回答的问题 |
|---|---|---|
| 1 | 需求提取与冻结（`需求说明.md`） | 题面到底要求什么、哪些是留白 |
| 2 | 交互原型（`demo/`） | 五个步骤能不能走通、异常能不能"看见" |
| 3 | 契约（`契约.md` + ADR） | 表长什么样、接口收什么、测试叫什么 |
| 4 | 实现 S1：状态机 4 → 7 | 取消 / 作废 / 删除各自从哪来往哪去 |
| 5 | 实现 S2：医院表 + 拜访快照 | 主数据能删，历史还能读吗 |
| 6 | 实现 S3：规则版本 + 判定快照 + 五个数字 | 改阈值会不会改写历史 |
| 7 | 实现 S4：读时收敛 | 没人操作时，超时由谁推动 |

P12–P16 发生在实现与交付阶段——**后半段的指令更短，因为约束已经写进文档了**。

| # | 指令（原文摘要） | 触发的最关键判断 |

| P3 | 「MR 默认页应是 plans list，可按开始时间/状态/异常类型排序」 | 列表先行；"异常类型"要能分组排序，不能按字符串排 |

| P5 | 「作废和删除该如何区分呢」 | 用**时间窗**而不是严重程度分：事前可删可取消，事后只能作废 |

| P7 | 「删除也是终态吧」 | 采纳为 `DELETED` 终态；同时把"计划超时"从作废改为**取消**（作废的前提是"人到了"） |
| P8 | 「操作按钮能否用三个点替换，只显示可用的操作」 | 菜单按状态渲染；不可用的动作不出现，但底部留一行说明 |
| P9 | 「使用快照方案，但数据库仍不删除，而是标记删除、不用于展示」 | 拜访快照 → 主数据可逻辑删除而历史不受影响；代价（改名不回溯）写进 ADR |

| P11 | 「哪些内容会是审计需要的？」 | 审计只问三件事：发生过吗 / 为什么这么判 / 事后动过吗。据此反推必须留存的字段 |
| P12 | 「产出契约：可追溯矩阵、数据模型、evaluation、API、分层边界」 | 先把**测试名**定死再写实现；契约里的 DDL 必须能真执行，写完当场跑一遍 |
| P13 | 「MR1 不应该可以为 MR2 创建计划」 | 授权是**按动作**判的，不是给列表加 WHERE。由此展开对整个写接口面的审计（§3.2） |
| P14 | 「先做这两件一分钟的事，然后开 S1」 | 把"恢复备份分支 / 清理临时分支"这类小事前置，避免和开发混在一个提交里 |

| P16 | 「检查需要提交的内容是否已经齐备」 | 从**干净克隆**验证，而不是在工作区里自测——这条直接抓到了§3.3 的定时炸弹 |

## 3. AI 纠偏案例

题面要"一次"，这里给四次，按发现方式排：**点出来 → 审出来 → 被需求推翻 → 跑出来**。

### 3.1 状态机：从 4 个状态到 7 个

> 发现手段：**在原型上点出来**。这一节按真实顺序记录四轮讨论。

#### 3.1.1 起点：AI 的"字面实现"

最初的状态机只有四个正向状态，全部来自题面的五个步骤：

```
PLANNED ──签到──► CHECKED_IN ──签退──► CHECKED_OUT ──补记录──► REPORTED
```

它是对的，也是**不完整的**：这条链路只能表达"去了、且走完了"，表达不了任何"没去成 / 去了不算"的现实。
而现实里，医生停诊、临时改期、走错院区每天都发生。

AI 当时的判断是"题面没写，就不做"——这是字面实现，不是需求理解。

#### 3.1.2 第一次发现：删除不该是一个数据标记

候选人提出"默认页应该是计划列表，能改、能删、能取消"。AI 的第一版实现是：

- 取消：`PLANNED → CANCELLED`（进状态机）
- 删除：**一个 `deleted` 字段**，从列表里过滤掉（不进状态机）

在 demo 上点了两次之后问题暴露出来：**删掉的计划去哪了？**

- 它不在"完成"里，不在"取消"里，也不在"作废"里；
- 看板的"计划执行率"因此算不出来——分母可以被删除任意收缩；
- 审计问"这条计划存在过吗"，答不上来。

**判断点**：删除不是"看不见"，而是一个**业务终态**。候选人的表述很直接——"删除也是个终态状态吧"。

于是 `DELETED` 进入状态机，并补了两条规则：
1. 删除**免原因**（它是纠错，不是业务事件）；
2. 但只有"创建后 1 小时内 + 距开始 > 1 小时"才允许，超出窗口只能取消（取消需原因、进取消统计）。

这一步把"删除"从数据层操作提升成了业务语义，也让 `取消 vs 删除` 第一次有了清晰边界：
**删除 = 本来不该存在；取消 = 主动放弃。**

#### 3.1.3 第二次发现：作废不该要审批（AI 的过度设计）

有了删除和取消，AI 接着加了"作废"，但设计成**两级审批**：

```
CHECKED_IN ──作废申请──► PENDING ──主管确认──► VOIDED
```

理由写得很"稳"：怕代表把异常拜访作废掉，所以要主管把关。
（后来主管整层被裁掉，这条设计连"谁来批"都无从谈起——见 §3.8。）

候选人直接否掉："不需要主管审核，直接作废。"

讨论后承认这是 **AI 的过度设计**：医生停诊是**高频事件**，如果每次作废都要等主管，代表会怎么选？
他会选择**不作废、直接走人**——让系统 24 小时后自动处理。结果是数据更脏，而不是更干净。

**判断点**：审批解决的是"信任问题"，但它把成本压在了每一次**正常**作废上。真正该做的是
**让作废无法掩盖事实**，而不是让作废变慢。于是改成：

- 代表自助作废，但**必须填原因**；
- 作废时**补跑 R1/R2**（用已有的签到时间与坐标），把 flags 存进作废记录；
- 看板把"作废"单列一栏，异常在作废记录里仍然可见。

这样作废只能让这条拜访"不计入完成"，不能让异常"没发生过"。
（当时写的是"主管能看到"；主管角色在 §3.8 被裁掉后，这一栏改由管理员看。）

#### 3.1.4 第三次发现：超时到底算取消还是作废

AI 第一版的超时扫描**只处理了"签到未签退"**——计划过期未签到根本没有任何出口，
会永远停在 `PLANNED`。这又是一次字面实现：题面里的"拜访"从签到开始，
所以 AI 只想到了签到之后的悬挂。

候选人指出："planned 超时 24 小时应该也是作废"。

但在实现时发现口径对不上：**作废的前提是"人到了"**（有签到证据），
而"计划过期没去"根本没有到过现场——把它记成作废，会让作废率混进一批
从没进过医院的人，这个指标立刻失去含义。

**判断点**：两条系统边，终点不同——

| 场景 | 终点 | 理由 |
|---|---|---|
| 计划时间 + 24h 未签到 | `CANCELLED`（NO_CHECKIN） | 没去成，属于取消 |
| 签到 + 24h 未签退 | `VOIDED`（TIMEOUT） | 去了但没走完，属于作废 |

这是本次协同里**唯一一次 AI 反过来修正候选人的口径**：作废只从 `CHECKED_IN` 出，
计划阶段的两个出口是「取消」和「删除」。

#### 3.1.5 第四次发现：作废窗口必须关在签退之前

AI 的第二版允许 `CHECKED_IN` 和 `CHECKED_OUT` 都能作废。

在 demo 上走一遍就看出问题：**签退之后，界面已经显示"异常 · 命中 2 项"，此时再点作废，
等于判定可以被撤销。**

**判断点**：作废与判定是"抢跑"关系——判定发生在签退，作废发生在判定之前，
代表就能在"估计要判异常"时提前作废。把作废收紧为**只允许 `CHECKED_IN`**，
这条路就由状态机本身堵死了（不是靠制度，是靠没有那条边）。

#### 3.1.6 收敛后的状态机

**7 个状态 · 8 条迁移**，其中两条是系统边：

```
PLANNED ──签到──► CHECKED_IN ──签退──► CHECKED_OUT ──补记录──► REPORTED
   │                  │
   ├─取消(需原因)─► CANCELLED          ├─作废(需原因)─► VOIDED
   ├─删除(免原因)─► DELETED            └─超时(系统)───► VOIDED
   └─超时(系统)──► CANCELLED
```

三个终态各归一个计数器：**完成**（CHECKED_OUT + REPORTED）/ **取消** / **作废**，删除不入账。

#### 3.1.7 复盘：AI 在这一轮里的四类错误

| 错误类型 | 具体表现 | 人的纠正方式 |
|---|---|---|
| **字面实现** | 题面没写退出路径，就不设计退出路径 | 用真实场景（停诊、走错院区）去压测状态机 |
| **过度设计** | 给作废加两级审批，理由"更安全" | 问"这个成本落在谁身上、多久一次"——高频场景下审批会逼出更差的行为 |
| **语义混淆** | 把"删除"当数据标记而不是终态 | 追问"这条记录还该不该被统计到"——能算进分母的才叫状态 |
| **漏掉出口** | 超时只处理了"签到未签退"，"计划过期"没有出路 | 拿状态逐个问"如果一直停在这里会怎样" |

共同点：**AI 的每一版单看都自洽，只有在"点一遍 + 问一句'那这条算哪一类'"时才暴露**。
所以这个 demo 的真正作用不是展示界面，而是**把状态机变成可以被质疑的对象**。

> 这一轮的产物：`demo/assets/state-machine-v2.svg`（图）与 `需求说明.md` 第 3 节（表）。
（状态机这一节的收尾：需求自己在实现前把「主管」整层砍掉了，`mr.team_id` 因此变成死字段。
教训已写进契约：**加一个字段只要一行 DDL，删掉它要改 ERD、契约、ADR 三处**。）

### 3.2 授权：AI 把「我是谁」实现成了「过滤列表的参数」

这一条比状态机那次更值得记，因为它**通过了所有测试**——测试是 AI 自己写的，自然测了 AI 自己的理解。

**症状**：运营同事用一个代表账号点了几下，说"这个代表好像能替别人建计划"。

**第一次定位**（只改了创建接口就以为完事）：

```bash
$ curl -X POST -H 'X-Actor: 张伟' -d '{"mrId":"李娜", ...}' /api/visits
403 forbidden: a rep may only create visits for themselves   # 修好了
```

**但顺手继续探了别的动作**，发现问题大得多：

```
张伟 checkin  李娜的拜访 → 409   （状态不允许——不是权限拦的）
张伟 checkout 李娜的拜访 → 200   ← 真的把别人的拜访签退了
张伟 cancel   李娜的拜访 → 409
张伟 delete   李娜的拜访 → 409
```

`409` 是**巧合**：那几个动作恰好因状态不对被拒。`checkout` 没有前置状态限制，直接成功——
**一个代表把另一个代表的拜访"完成"掉了，证据被毁，没有任何一处报错。**

**根因**：`X-Actor` 只被用在 `GET /api/visits` 和看板上，即"能看见什么"；六个写接口全都只按
id 操作，从不判断这行归谁。AI 把身份当成了**查询参数**，而不是**权限边界**。

**修复**：抽出唯一守卫，放在六个写接口最前面，`GET` 复用同一条规则：

```go
func (s *Server) authorizeVisit(w, r, ctx) bool {
    rec, err := s.repo.Get(ctx, r.PathValue("id"))
    if err != nil { → 404 }
    if actor 是代表 && rec.Visit.MRID != actor.MRID { → 403 }
}
```

**为什么不写七处 if**：这正是"第七个 handler 会忘"的那类规则——第一次实现时它被忘了六次。

**测试不只断言状态码**：

```go
// 六个动作都 403
// 然后断言：两行数据的 status 一点没变
```

只查 403 不够：一个"返回 403 但仍然写了库"的守卫会骗过状态码检查。

**第四次审计**（读接口）还漏了一个：`GET /api/catalog` 把全部同事名单发给每个代表——
造不了数据，但泄露了组织信息，且对这个角色毫无用处。现在代表只看到自己那一行。

**写进文档**：`契约.md` §5.2 加了一条硬规则——*授权是按动作判的，不是按列表判的*，
以及一张"哪个面由谁守"的表；`角色模型.md` R-ROLE-1 也补了同样的教训与具体失败形态。

### 3.3 我推翻了 AI 的一个设计前提：读时收敛不够

**背景**：超时作废（签到后 24 小时没签退）第一版是"读时收敛"——三个读接口在返回前跑一遍扫描。

**AI 当时的理由**（写在契约 §5.4）：
> 不需要调度器，就不会因为调度器停摆而失效；反过来，后台任务停了没人知道，状态会静默错误。

**我的反驳**：
> 这个理由只对"正在看的人"成立。一条 09:00 就该作废的拜访，如果没人打开页面，
> 到 18:00 数据库里仍然是 `CHECKED_IN`。报表、导出、BI、另一个服务读到的都是假状态。
> 合规系统里，"数据正确是因为恰好有人看了一眼"不是性质，是巧合。

**改法**：后台定时扫描为主（进程内 goroutine，默认 30 秒，`TIMEOUT_SWEEP_INTERVAL` 可配），
读时收敛保留为兜底。关键是没有重写判定逻辑——两条路调用同一个 `Converge`。

**顺手补的两个洞**（都是"从偶尔调用变成每秒调用"才显形的问题）：

1. `FOR UPDATE SKIP LOCKED` 原来跑在没有事务的 `Query` 上，语句结束锁就放了——两个读者可能选中同一行，
   后到的那个会撞上状态守卫。偶尔发生无害，但**后台任务每个周期都会重试**，警告会淹掉真问题。
   现在锁与写入在同一个事务里，`StateError` 被视为"别人已经做了"直接跳过。
2. `void_cause` 原来是"先写作废，再 UPDATE 补 cause"两步。中间崩了就会留下一条**原因错误的作废记录**——
   审计痕迹说谎比没有痕迹更糟。现在 cause 是 `voidInTx` 的参数，一条语句写对。

**证明**：`TestSweepVoidsWithoutAnyRead` 用裸 SQL 断言——不发任何请求，行也已经是 `VOIDED`；
`TestConcurrentSweepsApplyOnce` 四个扫描并发，`version` 只加一次。

### 3.4 定时炸弹：一个测试的保质期只有一天

**怎么发现的**：不是跑测试，是**从干净克隆跑测试**。

```bash
$ git clone <repo> && go test ./...
--- FAIL: TestCreateVisit
    plannedAt must not be in the past
```

测试里写死了 `2026-11-02T10:00:00`。写的时候是未来所以通过；**跑的时候正好是 2026-11-02，
于是变成过去**。也就是说这份代码昨天能过、今天不能过、以后永远不能过。

**为什么工作区里一直是绿的**：我一直在改代码的那个目录里跑测试，日期写死的问题只在"换一天"
或"换一个克隆"时才暴露——而这两件事恰好都发生在评审那天。

**修复**：四处硬编码时间改成 `time.Now().Add(48h)`；那个故意的 `2020-01-01`（用来断言拒绝）保留。

**教训**：绿色只对"我刚跑过的那个环境"成立。所以交付前必须从**干净克隆**验证一次，
`go build` + `go test` + `npm ci` + `npm run build` 全走一遍——这一步现在已经写进 README。
